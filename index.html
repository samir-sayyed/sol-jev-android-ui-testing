01 / DESIGN NOTE

Spend reasoning where it changes the next step.

A strong model turns a natural language scenario into explicit actions and checks. A local runner executes that plan, asking Jev small visual questions when the UI tree cannot answer them.

PLANNING

Sol keeps scenario authority.

Sol defines permitted actions, expected states, stop conditions, and recovery limits. It returns when a new decision requires reasoning. The runner acts under those rules.

EXECUTION

Each action still earns its next step.

Capture fresh evidence, resolve a target, perform one action, and verify its outcome. Fewer planner requests must preserve every required test assertion.

The change that saves round trips

Sol can preauthorize transitions such as “when the schedule form is visible and fixture values match, tap Save.” Local code evaluates the condition. If Sol must choose every individual tap live, its latency remains on every step.

This applies the narrow decision pattern demonstrated by audio action systems to mobile UI observations. The design uses Sol, Jev, and a device adapter. Its speed and accuracy are hypotheses to test against a measured baseline.

02 / DESIGN NOTE

03 / DESIGN NOTE

The execution loop is small and strict.

Every iteration starts from a fresh observation of the selected device. A successful action advances the scenario only after the required outcome is verified.

  1. Observe. Capture foreground package, rotation, screen dimensions, UI hierarchy and an observation ID. Capture a screenshot when a visual check is needed.
  2. Resolve locally. Match a unique visible, enabled element by resource ID, test tag or accessibility label. Ambiguous matches remain unresolved.
  3. Ask Jev when useful. Supply the current image and a small set of questions tied to this step. Inspect presence separately from coordinates.
  4. Validate. Check allowed action, target bounds, observation freshness, package, rotation and remaining budget.
  5. Act once. Execute through the selected adapter. Serialize all device mutations; consume results before continuing.
  6. Wait and assert. Wait for a specific outcome within a deadline. Record passed, failed, blocked or infrastructure error.

Runner control flow — pseudocodepython
# Pseudocode: interfaces below must be implemented by the runner.
# All required assertions come from the frozen test specification.
def run_step(step, spec, device, jev, planner, budgets):
    before = device.observe()
    ensure_selected_serial_package_and_rotation(before, spec)
    require_preconditions(step, before)

    target = find_unique_enabled_visible_node(before.tree, step.action.target)
    if target is None and step.visual_fallback is not None:
        answers = jev.inspect(before.image, step.visual_fallback)
        target = accept_visual_target_or_none(answers, before)

    if target is None:
        # No tap on uncertain evidence; a budgeted replan may help navigation.
        return planner.request_navigation_plan(compact_evidence(before), spec)

    require_fresh_observation_and_allowed_action(before, target, budgets)
    device.execute(step.action, target)  # Exactly one side-effecting action.
    after = device.wait_for(step.wait_for, deadline=budgets.deadline)
    result = evaluate_required_assertions(spec, step, after)
    record_step(before, target, after, result)

    if result.is_known_false:
        return Failed(result.evidence)
    if result.is_unknown:
        return Blocked(result.evidence)
    return Advance(next_step=step.next_id)

A replan may repair navigation or fixture setup. It cannot remove a required step, rewrite the expected result, or convert a failed assertion into a successful run.

PLAN VALIDATION

Reject free-form commands.

Allow a fixed action enum: launch, tap, input, swipe, back, wait and assert. Validate target fields, package scope, timeouts and budgets. A plan contains typed data rather than arbitrary shell code.

SPEC INTEGRITY

Freeze pass criteria.

Hash the scenario, fixture and required assertions. Keep that hash across replans. Planner-generated navigation may change; the original pass criteria remain attached to every run.

Prefer device or application state for exact values, counts, saved data and system settings. Use visual assertions for appearance and visual accessibility questions. A success banner alone does not establish that a schedule was persisted or that sound policy changed.

05 / DESIGN NOTE

Give Jev questions that code can act on.

A single screenshot can support screen classification, target presence and localization in one request. The runner interprets the answers under the plan’s rules.

CHOICE

Which screen is visible?

Use a small set of relevant screen classes and include an unknown or other option. Compare the selected answer and its probabilities against validation data.

NOUL

Is the required thing present?

Ask a concrete yes/no question. The response carries a probability under the noul field. It does not use the Box confidence field.

BOX

Where is this one target?

Request a normalized rectangle around a precisely described target. Match duplicate controls by surrounding context, or return to other evidence.

Request and answer fields: TypeSafe API, Choice, Noul, Box.

A box needs a presence gate.

Box returns coordinates even when the target is absent. Require positive presence evidence and suitable Box confidence before accepting coordinates. Tune thresholds on held-out app screenshots; no universal threshold is assumed. Box documentation

The example illustrates request construction, not a complete production adapter. Add response validation, API error classification, bounded retries with Retry-After handling, tracing and cancellation. Never retry a device action blindly because a model request failed.

Batch independent questions about the same observation. Dependent actions remain sequential. TypeSafe documents parallel question evaluation; benchmark the actual image workload and request size. Batching pattern

06 / DESIGN NOTE

Keep observation and coordinates aligned.

Hierarchy selectors should handle ordinary controls. Coordinate input needs additional checks because a correct box on an old or transformed image can still produce the wrong tap.

IMAGE PIPELINE

Capture → prepare → map.

Keep the original device dimensions and crop rectangle. Resize uniformly. Track the observation ID and rotation. Use a larger relevant crop when small text loses detail.

TARGET PIPELINE

Presence → uniqueness → freshness.

Reject absent, obscured, duplicate or stale targets. Any intervening device action invalidates prior target evidence. Reobserve after a rotation or unexpected foreground change.

Current image limits include PNG/JPEG, 256–1568 pixels per side and a minimum total area of 78,400 pixels. A small crop may need padding or scaling. Preserve every transform so normalized edges map back to device pixels. These features are experimental. Image limits and preparation

Coordinate transform — resized crop to original devicepython
import math

def box_center_on_device(box, crop, device_size):
    # crop is (left, top, width, height) in original device pixels.
    # Image was resized uniformly, without rotation or letterboxing.
    left, top, right, bottom = (
        float(box[k]) for k in ('left', 'top', 'right', 'bottom')
    )
    if not all(math.isfinite(v) and 0 <= v <= 1
               for v in (left, top, right, bottom)):
        raise ValueError('Invalid normalized box')
    if left >= right or top >= bottom:
        raise ValueError('Empty box')
    cx, cy, cw, ch = crop
    dw, dh = device_size
    if cw <= 0 or ch <= 0 or cx < 0 or cy < 0 or cx + cw > dw or cy + ch > dh:
        raise ValueError('Invalid crop transform')
    x = round(cx + ((left + right) / 2) * cw)
    y = round(cy + ((top + bottom) / 2) * ch)
    if not (0 <= x < dw and 0 <= y < dh):
        raise ValueError('Tap falls outside device')
    return x, y

This function assumes no letterboxing or rotation. If either is applied, extend the transform explicitly. Range checks cannot prove that a box identifies the intended control; semantic and freshness checks remain necessary.

Retain raw ARTEMIS initially.

Use the same device transport in baseline and hybrid runs. That isolates the effect of model routing. A direct ADB adapter can be compared afterward.

RUNTIME

Use a long-lived local process.

Reuse HTTP connections, keep compact state and emit structured events. Keep screenshots outside the planner transcript unless needed. Limit context to the current step and relevant recent failures.

Use Python with typed contracts and a JSON Schema or equivalent validator. Store provider credentials in environment variables or an OS credential store. The HTML is a design blueprint: the module tree and runner pseudocode describe code to build; they are not an installed mobile testing package.

08 / DESIGN NOTE

Remove avoidable work before changing models.

The largest opportunity is avoiding repeated planner requests on steps that are already specified. Secondary gains come from compact observations and fewer unnecessary network calls.

Known paths should lean on deterministic selectors and exact assertions. Visual branches ask Jev. New or ambiguous paths return to Sol. This is a routing strategy; using two models by itself does not establish a performance improvement.

11 / DESIGN NOTE

Implement in six measurable stages.

Each phase has an exit condition. Build a working deterministic core before adding probabilistic visual decisions.

0

Measure current loop

Wrap existing Sol + raw-device workflow with per-stage timers and usage recording. Keep transport unchanged.

Exit check Baseline run bundles include capture, hierarchy, model, action, wait, assertion and total elapsed time.

1

Implement deterministic runner

Add typed contracts, serial selection, fake device, conditional waits, allowed actions and immutable assertions.

Exit check Three known fixture scenarios complete; stale targets, duplicate IDs and wrong package are rejected.

2

Add Jev adapter

Build image preparation, batched questions, response validation and normalized box mapping.

Exit check Absent targets never trigger taps in the labeled suite; malformed responses and timeouts produce explicit stops.

3

Calibrate visual routing

Label screenshots with present/absent/duplicate/occluded targets. Tune gates on training data, evaluate held-out screens.

Exit check Report target accuracy, accepted error rate and abstention by screen family, theme and device configuration.

4

Connect Sol planner

Expose run_scenario and resume_with_plan. Validate structured plans; send compact evidence for bounded replans.

Exit check Unknown screens can request help; failed assertions remain failed across replans; budgets terminate loops.

5

Run comparable benchmarks

Replay matched scenarios with deterministic fixtures across baseline, hierarchy runner and Jev runner.

Exit check Publish latency distributions, total spend, false passes, blocked runs and artifacts before rollout.

Test the harness where wrong behavior matters: stale observations, coordinate transforms, deadline expiry, cancellation, response parsing, double execution and assertion preservation. Explore actual app paths before authoring device test cases, using observed labels and stable selectors.

A cheap run that misses a bug is a worse test. Keep reliability visible alongside latency and spend.

Proposed rollout gates — configurable targets

Maintain baseline completion quality. Observe zero false passes in the seeded pilot. Target at least 20% lower median elapsed time and 50% lower model spend per correct completion. These are acceptance targets, not achieved results; also examine p95 and confidence intervals.

Seed failures deliberately: missing Save button, duplicate Save controls, wrong saved time, blocked permission, crash, obscured dialog and failed persistence. Review evidence independently of model verdicts. Report sample counts and uncertainty; zero observed errors in a small suite does not prove zero error probability.

14 / DESIGN NOTE

Keep the claims narrower than the evidence.

The architecture is implementable, but its advantage depends on workload, request latency, UI accessibility and how often the planner must return.

GOOD CANDIDATES

Repeated scenarios with occasional visual ambiguity.

Most navigation is predictable. Stable selectors cover routine actions. Jev handles a minority of visual-only decisions, and Sol returns on unfamiliar states.

HARDER CASES

Changing screens and frequent exceptions.

Animation, small controls, long waits and frequent replans reduce the opportunity. Inspect the actual per-stage trace before adding more model calls.

  • Jev image and Box support is experimental. Pin the tested model version and repeat calibration before upgrading.
  • Cloud inference includes network latency; a fast classification number does not establish fast end-to-end device actions.
  • A valid structured answer can still be wrong. Gate actions with independent state and target checks.
  • Use staging fixtures. Send only the UI evidence needed for each question; keep API keys outside page source and public artifacts.
  • Known assertion failures end the test. Distinguish them from uncertain perception and infrastructure failures.

Model version and feature status: Models and Images. No numerical speedup, latency or cost saving has been measured for this proposed runner.
